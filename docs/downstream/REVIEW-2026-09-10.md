## 5 — Hermes calendar attribution

[Tokscale #993](https://github.com/junhoyeo/tokscale/issues/993) remains open. The maintainer explicitly confirms that the parser groups cumulative model usage by session start time, so long-lived sessions are assigned to the wrong day. The maintainer prefers documenting missing information over inventing a precise-looking distribution. The model bucket timestamps are not per-call timestamps and cannot recover past usage distributions.

[Hermes #92151](https://github.com/NousResearch/hermes-agent/pull/92151) proposes an `api_call_usage` detail table with per-call timestamps. It remains open/unmerged. Current Hermes main's schema contains `session_model_usage`, not `api_call_usage`. Automated review notes retention, observability of failed inserts and aggregate/detail consistency; these are suggestions, not maintainer acceptance. Historical calls cannot be reconstructed by this future schema either.

Conclusion: the issue is real and community work exists. Do not propose another observed-delta ledger as an exact fix. Keep the local adapter explicitly provisional, follow the Hermes detail-table contract and then Tokscale parser support. No production Hermes schema migration or source upgrade was performed.

## 4 — activity timestamp semantics

Current Tokscale main's `ModelUsageJson` in `crates/tokscale-cli/src/main.rs` does not emit activity timestamps for the grouped JSON used by TokenMonitor. Parsing individual Codex events accurately does not change this output contract.

TokenMonitor's `sessionTimestampMap` reads the last JSONL timestamp and can fall back to file mtime. It is generic session activity, not specifically a token-bearing event. A synthetic rollout with a 10:00 token event and a 10:10 non-token response record produces 10:10 from upstream-compatible metadata enrichment and 10:00 from the local token-only tail adapter. This proves the semantic difference, not that generic activity is categorically a bug.

Focused issue/PR searches in Tokscale and TokenMonitor did not locate an exact existing contribution adding last-token activity to this grouped output. That is not proof no discussion exists. Before filing a patch, agree on whether the UI wants session activity or token-consuming activity, then prefer a structured timestamp from the data producer; do not duplicate tail scans merely because the current dates differ.

## 1 — persistence: actual cost versus claims

Observed current Hub (already throttled), two devices, snapshot about 723 KB:

- 45-second read-only sample: 9 snapshot replacements; process write_bytes increased 6,656,000 bytes.
- Sustaining this sample would be about 12.8 GB/day of process-accounted writes. This is an extrapolation, not measured daily usage or physical NAND writes.
- Synthetic snapshot of matching size, 50 atomic write/rename iterations: median 3.29 ms, P95 7.50 ms, maximum 13.30 ms. Synthetic content only; no production files overwritten. Warm-cache, local VM, no fsync: not a durable-write latency benchmark or a before/after ingest-rate test.
- The visible disk is a QEMU virtual disk. Physical medium, endurance, host write amplification and SMART wear are unknown. There is no evidence here of physical disk damage, pathological latency or a user-visible problem.

Upstream writeJsonAtomic uses writeFileSync plus rename, without file/directory fsync. Immediate writing is not a strict power-loss durability guarantee; delaying it adds a separate process-crash window for acknowledged updates still held only in memory. Neither implementation should be described as a durable transaction log.

Conclusion: reduce priority of the generic persistence PR. It is a configurable I/O optimization, not an established disk-health repair. Keep the deployed behavior untouched for now. If proposing upstream, first measure representative unthrottled ingest rates and response latency, retain immediate-write behavior by default, and explain the additional crash-loss window. Do not expand the scheduler based only on fear of SSD wear.
